# DEVOPS_GUIDE — план документа (черновик v0)

> Язык: русский.  
> Формат работы: инкрементальный — в этом коммите только outline и chapter plan, без детальной проработки процедур.

## 0) Источники истины и режим ведения документа

### Primary sources (обязательная привязка)
1. `docs/architecture.md` — архитектурные границы и компоненты.
2. `ROADMAP.md` — этапы изменений и релизные приоритеты.
3. `docs/progress.md` — фактический прогресс и текущий статус.

### Правило обновления глав
- Каждая глава DEVOPS_GUIDE должна иметь блок **«Проверено по источникам»** с ссылками на пункты из трёх документов выше.
- При расхождении данных приоритет такой:
  1) `docs/architecture.md`
  2) `docs/progress.md`
  3) `ROADMAP.md`
- Если данных не хватает — фиксируем **TODO/Assumption** и не придумываем недостающие факты.

## 1) Цели гида

Сделать практический операционный гайд для этого репозитория (как для реальной системы), покрывающий:
- деплой;
- обновление;
- откат;
- бэкап/восстановление;
- мониторинг;
- CI/CD.

Фокус: **runbook-first** (что делать по шагам), а не академические объяснения DevOps.

## 3) План инкрементальной разработки глав (chapter plan)

### Итерация A (foundation)
**Результат:** главы 1–2 в рабочем виде + словарь терминов.
- Собрать факты по архитектуре, окружениям и зависимостям.
- Определить эксплуатационные ограничения и риски.
- Зафиксировать минимальные SLI/SLO для старта.

### Итерация B (delivery)
**Результат:** главы 3–5 (deploy/update/rollback) как полноценные runbook’и.
- Описать пошаговые команды и точки контроля.
- Добавить smoke и rollback criteria.
- Добавить decision tree: обновлять / откатывать / roll-forward.

### Итерация C (resilience)
**Результат:** главы 6–7 (backup/restore/monitoring).
- Формализовать backup scope и restore drill.
- Описать карту метрик/логов/алертов.
- Добавить алерт-плейбуки на типовые сбои.

### Итерация D (automation)
**Результат:** глава 8 + чек-листы из главы 9.
- Зафиксировать CI/CD-пайплайн и quality gates.
- Формализовать релизный процесс и контроль изменений.
- Добавить «Definition of Done» для операционных задач.

### Итерация E (operational readiness)
**Результат:** приложения (глава 10) и финальный аудит консистентности.
- Унифицировать шаблоны runbook/postmortem.
- Проверить связность с архитектурой/roadmap/progress.
- Подготовить версию v1.0 для командного использования.

## 4) Критерии готовности каждой главы

Глава считается готовой, если:
1. Есть пошаговый runbook с командами и expected outcome.
2. Есть раздел «Failure modes / что может пойти не так».
3. Есть раздел «Проверено по источникам».
4. Есть измеримые критерии успеха (SLO, время восстановления, smoke checks).
5. Есть явные условия эскалации.
